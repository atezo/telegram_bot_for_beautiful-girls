# Бот записи: один мастер — один Telegram-бот

Один `compose.yaml` запускает отдельные контейнеры мастеров. Каждый контейнер имеет свой
токен Telegram, конфиг, календарь и постоянный том с SQLite. Дополнительная база, веб-сервер,
домен, OAuth-приложение и Google Cloud не нужны. Соединения с Telegram и CalDAV исходящие.

## Календарь

По умолчанию используется **Яндекс Календарь через CalDAV** (`https://caldav.yandex.ru`).
Мастер создаёт в Яндексе два календаря:

- **Рабочие часы** — отмечает, когда он работает в каждый конкретный день.
- **Записи** — подтверждённые ботом приёмы, связанные перерывы и личная занятость.

Например, в понедельник мастер создаёт рабочее событие 14:00–18:00, во вторник два события
09:00–12:00 и 16:00–19:00, в среду ничего — выходной. Повторения необязательны.
Можно поставить повторение для обычного графика и изменить отдельные дни.
Название рабочего события любое; его начало и конец задают доступные часы. События
«выходной» в календаре рабочих часов создавать не нужно: отсутствие рабочих часов
означает отсутствие доступной записи.

Клиент сначала выбирает услуги, затем бот ищет подходящее время в этих рабочих часах,
учитывая длительность, занятость и перерыв. Сетка времени задаётся `step_minutes`;
она не определяет рабочий график. Разрешение завершить после рабочих часов — `overtime`.

В Яндекс ID создайте **пароль приложения для Календаря (CalDAV)**. Используйте его,
а не основной пароль аккаунта. Яндекс Cloud и регистрация приложения разработчика не нужны.
[Официальная инструкция](https://yandex.ru/support/yandex-360/customers/calendar/web/ru/data-exchange/synchronization/sync-desktop).
[Бесплатное использование сервисов Яндекс 360](https://360.yandex.ru/blog/b2c/neochevidnye-pomoshniki-v-uchyobe-disk-kalendar-i-telemost-ot-yandeks-360/).

Адаптер использует стандартный CalDAV; создание, перенос, удаление и повторения проверены
на локальном Radicale. Живая совместимость с конкретным аккаунтом Яндекса ещё требует
проверки с его реквизитами. Настройка другого CalDAV-сервера предусмотрена через URL.

## Первый запуск

1. В [@BotFather](https://t.me/BotFather) создайте **отдельного бота для каждого мастера**.
2. Подготовьте числовой Telegram ID мастера.
3. Создайте два календаря и пароль приложения, как описано выше.
4. Скопируйте шаблон и заполните конфиг:

```sh
cp config/master.example.toml config/anna.toml
```

```toml
bot_token = "ТОКЕН_БОТА_АННЫ"
bot_username = "anna_booking_bot"
master_id = 123456789
master_name = "Анна"
timezone = "Europe/Moscow"
approval_minutes = 120
break_minutes = 20
lead_minutes = 60
step_minutes = 30
overtime = true
caldav_url = "https://caldav.yandex.ru"
caldav_username = "anna@yandex.ru"
caldav_password = "ПАРОЛЬ_ПРИЛОЖЕНИЯ_CALDAV"
hours_calendar = "Рабочие часы"
bookings_calendar = "Записи"
```

Названия календарей должны точно совпадать. При одинаковых названиях у нескольких календарей
укажите полные CalDAV URL вместо названий. Календари нужно создать вручную: бот их не создаёт.

Конфиги содержат секреты и исключены из Git и Docker build context. Контейнер читает их
из read-only bind mount под UID 10001: на Linux установите владельца `10001:10001`
и права `600` для файлов (или настройте эквивалентный доступ через ACL). Не делайте файл
общедоступным и не отправляйте токены/пароли в чат.

5. Запустите первый контейнер:

```sh
docker compose up -d --build bot-anna
docker compose logs -f bot-anna
```

6. Мастер открывает собственного бота и нажимает **Start**. По `master_id` бот сразу
   показывает меню владельца. Регистрации через `/master` нет.
7. Через **Мои услуги → Добавить услугу** мастер вводит, например:
   `Маникюр | 2500 | 90` (рубли и минуты).
8. Клиентам передаётся обычная ссылка `https://t.me/anna_booking_bot`.

Бот не может первым начать переписку с мастером: нажать Start один раз необходимо для
уведомлений Telegram. Это не подключение и не регистрация мастера; все реквизиты уже в конфиге.

## Несколько мастеров в одном Compose

В `compose.yaml` уже есть `bot-anna` и пример `bot-maria`. У каждого свой том и конфиг:

```
compose.yaml
├── bot-anna  → config/anna.toml  → anna_data
└── bot-maria → config/maria.toml → maria_data
```

Скопируйте шаблон в `config/maria.toml`, укажите другого бота, Telegram ID мастера и
реквизиты его календаря. Запуск обоих в **одном Compose-проекте**:

```sh
docker compose --profile maria up -d --build
```

Профиль нужен только чтобы пустой пример второго мастера не мешал первому запуску.
Можно убрать `profiles: [maria]`, и оба контейнера будут запускаться обычным `up`.
Для следующего мастера скопируйте блок сервиса, задайте другой путь конфига и новый том.
Не используйте один токен бота или один том базы для двух мастеров.

Ни один контейнер не публикует порт. Сервер может находиться за NAT: нужны только исходящие
соединения в интернет. Уведомления о правках календаря получаются периодическим опросом.

### Переменные окружения вместо файла

Любое поле конфига можно задать переменной с тем же именем в верхнем регистре:
`MASTER_ID`, `BREAK_MINUTES`, `CALDAV_PASSWORD` и т.д. Env имеет приоритет над TOML.

Чтобы использовать только env, уберите `CONFIG_FILE` и bind mount конфига у конкретного
сервиса, добавьте `env_file: ./config/anna.env`. Пример полей — `.env.example`.
Файлы `config/*.env` тоже не должны попадать в Git.

Имя, часовой пояс, срок подтверждения, перерыв и прочие параметры применения конфига
обновляются при перезапуске. После правки TOML:

```sh
docker compose restart bot-anna
```

При изменении `environment`/`env_file` пересоздайте контейнер:

```sh
docker compose up -d --force-recreate bot-anna
```

В меню мастера настройки показаны для справки. Услуги и цены мастер редактирует через
кнопки в боте; рабочие часы — непосредственно в календаре.

## Как работает запись

1. Клиент выбирает услуги, дату, время, вводит имя/контакт и подтверждает заявку.
2. Мастер получает карточку с услугами, стоимостью и временем, кнопки подтверждения/отказа.
3. До решения весь приём вместе с перерывом зарезервирован в базе.
4. После подтверждения создаются встреча и отдельный блок перерыва в календаре.
5. Только после успешного создания клиент получает подтверждение.

Срок подтверждения настраивается в минутах и ограничен началом приёма. Просроченная заявка
освобождает время и уведомляет стороны. Старую кнопку подтверждения использовать нельзя.

Приём 14:00–15:30 и перерыв 20 минут занимают время до 15:50. Перерыв применяется ко всей
записи. Если `overtime = true`, приём может завершаться после конца отмеченных рабочих часов;
мастер увидит предупреждение. При `false` сам приём должен полностью помещаться в рабочие
часы. Завершающий перерыв может выходить за график. Пересечения с занятостью запрещены.

Изменение услуг и настроек не меняет цену, длительность, перерыв и срок уже созданной заявки.
Перед подтверждением повторно проверяются актуальные рабочие часы и занятость.

## Отмены и переносы

- Клиент: `/my` → запись → **Отменить** / **Перенести**.
- Мастер: Start → **Заявки и записи** → действие.
- При переносе новая заявка проходит подтверждение. До него старая запись сохраняется.
  При отказе или истечении срока переноса клиент не теряет исходный приём.
- После подтверждения новой встречи старая удаляется отдельной повторяемой операцией:
  во время сбоя она может ненадолго оставаться в календаре.
- Удаление приёма из календаря уведомляет клиента и удаляет связанный перерыв.
- Перемещение приёма в календаре уведомляет клиента и перемещает перерыв.
- Удалённый/перемещённый вручную перерыв восстанавливается по параметрам записи.
- **Закрыть период / отменить приёмы** показывает список затронутых записей и после
  подтверждения отменяет их, уведомляя клиентов. Конец периода не включается.
- **Открыть закрытый период** разрешает новые записи, но не восстанавливает отменённые.
- Удаление рабочего события не отменяет подтверждённые приёмы автоматически: мастер
  получает предупреждение о записи вне расписания.

Обычная личная занятость (обед, учёба, поездка) добавляется в календарь «Записи». Другие
календари аккаунта не участвуют в расчёте. Не превращайте созданный ботом приём в повторяющуюся
серию: одна запись клиента соответствует одному событию.

## Надёжность и ограничения

- Синхронизация идёт примерно раз в минуту плюс время API; доставка очереди сообщений —
  каждые несколько секунд. В момент сбоя резервы сохраняются до завершения обработки.
- SQLite использует транзакции с `BEGIN IMMEDIATE`; два клиента не займут один интервал.
  Каждый контейнер хранит свою базу в своём локальном Docker volume. Не используйте общий
  файл SQLite или сетевую файловую систему. Установлена блокировка против двух процессов
  на одном файле базы.
- Статус и очередь уведомлений сохраняются одной транзакцией; события имеют постоянные UID.
  После перезапуска операции повторяются без создания нового UID.
- CalDAV и база не имеют общей транзакции: ручная правка календаря одновременно с
  подтверждением может создать пересечение. Бот обнаружит его при следующей синхронизации
  и предупредит мастера.
- При сетевой неопределённости Telegram может повторно доставить сообщение; при блокировке
  бота клиентом мастер получает сообщение о недоставке.
- Секреты CalDAV хранятся в конфиге/env, не в базе и не в сообщениях. Пароль приложения
  может давать доступ к календарям аккаунта; бот использует только два выбранных календаря.
- Первая версия: 60 дней вперёд, до 70 услуг в каталоге, до 10 услуг в одной записи,
  суммарно до 24 часов, одна ожидающая заявка клиента у мастера.
- Платежей, листа ожидания и напоминаний за сутки пока нет.
- Не подключайте существующую базу к другому мастеру. Перенос старой Google-версии на
  CalDAV с живыми записями потребовал бы отдельной миграции событий; автоматически он не выполняется.

## Резервные копии

SQLite можно скопировать согласованно через встроенный backup API без остановки бота:

```sh
docker compose exec -T bot-anna python -c "import sqlite3; a=sqlite3.connect('/data/booking.db'); b=sqlite3.connect('/data/backup.db'); a.backup(b); b.close(); a.close()"
docker compose cp bot-anna:/data/backup.db ./anna-backup.db
```

Храните резервные копии с ограниченными правами, отдельно сохраните конфиг с секретами.
Не выполняйте `docker compose down -v`: это удаляет постоянные тома. При обычном обновлении:

```sh
docker compose up -d --build
```

Автоматическое создание начальной схемы есть, миграций для будущих изменений схемы пока нет.

## Тесты

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest tests -q
```

Интеграционные тесты поднимают временный Radicale только на `127.0.0.1`, создают свои
календари и завершают процесс после проверки. Настоящие Telegram и Яндекс не затрагиваются.

Локальный запуск без Docker:

```sh
CONFIG_FILE=config/anna.toml .venv/bin/python -m app.main
```

База по умолчанию `booking.db`; для нескольких локальных процессов задавайте разные
`DATABASE_URL`. На сервере рекомендуется пользоваться подготовленным Compose.
